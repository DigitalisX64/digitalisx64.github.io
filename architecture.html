1. End-to-End Pipeline

When you launch an arm64-v8a APK on a Digitalis emulator, Android's NativeBridge hands control to libberberis_arm64.so. From that point every ARM64 instruction inside the app and its libraries flows through the translator until it reaches the host x86_64 CPU or GPU. Hover any node for details.

2. Dual Dispatch — JIT and Interpreter

Every ARM64 instruction is handled by one of two execution engines. The JIT covers the fast path; the interpreter is the safety net.

Lite Translator (JIT)

Translates contiguous ARM64 regions to native x86_64 machine code. Output is stored in a per-process translation cache and reused on subsequent entries. Handles integer ops, branches, loads/stores, system instructions, and most NEON/SIMD.

~98% of instructions

Interpreter (Fallback)

Per-instruction execution for things the JIT punts on: syscalls, complex SIMD (pairwise, widening, permute, across-lanes, CRC32), scalar conversions, and any decoder edge case. A region terminates JIT compilation when it hits an interpreter-only opcode.

fallback path

When the dispatcher reaches a guest PC for the first time, the decoder peeks at the instruction. If the JIT can handle it, a region is compiled. If not, a special kInterpreted marker is installed at that PC so the next entry routes straight to the interpreter — avoiding infinite recompile loops.

3. Worked Example — One Instruction at a Time

Click a tab to walk through the actual ARM64 → x86_64 transformation the JIT emits. The x86_64 listings assume RBP points at ThreadState and that the source guest registers are spilled (worst case — pinned registers produce shorter code).

ADD X0, X1, X2 — add two registers

ARM64 source

; ARM64 (4 bytes, little-endian)
ADD X0, X1, X2     ; 0x8b020020

31-bit encoding: sf=1 (64-bit) op=0 (add) S=0 (no flags) shift=00 Rm=X2 imm6=0 Rn=X1 Rd=X0.

JIT emits (x86_64)

mov  rax, [rbp + x1_off]  ; load guest X1
add  rax, [rbp + x2_off]  ; add guest X2
mov  [rbp + x0_off], rax  ; store back as X0

Three host ops, no flag emission (no ADDS). If X1 or X2 are already pinned to an x86 register the loads collapse away.

MOVZ X0, #0x1234 — zero-extend immediate

ARM64 source

; ARM64
MOVZ X0, #0x1234   ; 0xd2824680

MOVZ writes a 16-bit immediate into a 64-bit register, zeroing the other bits. ARM64 has no single “load any 64-bit immediate” instruction; bigger constants compose MOVZ + up to three MOVKs.

JIT emits (x86_64)

mov  qword [rbp + x0_off], 0x1234

Single store; x86 can move 32-bit immediates directly to memory and zero-extend.

LDR X0, [X1, #16] — load with offset

ARM64 source

; ARM64
LDR X0, [X1, #16]  ; 0xf9400820

Loads 8 bytes from the address X1 + 16 into X0. ARM64 unsigned-offset form, imm12=2 scaled by 8.

JIT emits (x86_64)

mov  rax, [rbp + x1_off]  ; guest pointer
mov  rax, [rax + 16]      ; guest load (host SIGSEGV  
                          ; handler forwards to guest)
mov  [rbp + x0_off], rax  ; store result as X0

The interpreter version wraps this in FaultyLoad so the host SIGSEGV handler can deliver a synthetic guest signal — a raw memcpy would crash the host process.

CBZ X0, .Ltarget — compare and branch if zero

ARM64 source

; ARM64
CBZ X0, .Ltarget   ; 0xb4000020

Branches to .Ltarget if X0 == 0. Does not touch NZCV.

JIT emits (x86_64)

cmp  qword [rbp + x0_off], 0
je   L_target_host        ; emit-time-known
                          ; fall through =  
                          ; next guest instr

Forward branches inside the region are resolved to host labels. Out-of-region branches end the region with an exit stub that returns to the dispatcher with the new guest PC.

BL <symbol> — branch with link (call)

ARM64 source

; ARM64
BL  foo            ; 0x94000000
                   ; + signed imm26<<2 offset

Writes the return address (PC + 4) into X30 (LR), then jumps to the call target.

JIT emits (x86_64)

mov  qword [rbp + x30_off], ; LR ←
     <next_guest_pc>      ; PC + 4
mov  rax, <callee_pc>     ; guest PC of foo
ret                       ; exit to dispatcher

BL always terminates the JIT region. The dispatcher looks up <callee_pc> in the translation cache and enters the callee.

4. Register Mapping

ARM64 exposes 31 general-purpose registers (X0–X30) plus SP and PC. x86_64 has 16. After reserving RAX for the guest PC, RBP for the ThreadState pointer, and RSP for the host stack, the JIT has 13 GP slots to pin guest registers into. Anything that doesn't fit lives in ThreadState memory and is spilled to/from a temp on demand.

x86_64 host pool (13 slots)

  • RBX
  • RSI
  • RDI
  • R8
  • R9
  • R10
  • R11
  • R12
  • R13
  • R14
  • R15
  • RDX *
  • RCX *

* RDX/RCX are reserved by specific x86 ops, so the allocator saves and restores them around DIV/MUL and variable shifts.

x86_64 reserved

  • RAX → guest PC
  • RBP → ThreadState *
  • RSP → host stack

ThreadState memory

  • X0…X30 (spilled)
  • SP
  • NZCV
  • V0…V31

When all 13 pool slots are taken and another guest register is needed, the allocator picks a temp, loads the guest value from ThreadState, uses it, and stores it back — rather than terminating the region. This keeps JIT regions long enough to amortize entry overhead.

5. Translation Lifecycle

What happens between an ARM64 byte sequence in memory and an x86_64 byte sequence the host CPU executes.

On region exit (a branch out, a syscall, register pressure, a JIT-unsupported opcode), control returns to the dispatcher with a new guest PC and the loop repeats.

6. Translation Cache Anatomy

The translation cache is the data structure that turns the runtime cost of binary translation from “every instruction” into “every region, once.” It is per-process, lives in writable + executable memory, and is keyed by guest PC.

Why region-based?

Per-instruction translation overhead is fatal. Region caching makes the marginal cost of a translated instruction approach the cost of an x86 instruction, plus the amortized cost of one translation.

What ends a region?

An out-of-region branch, a syscall, a call/return, exhausting the x86_64 register pool, or hitting an instruction the JIT can't handle. The region writes its exit pc back to RAX and rets to the dispatcher.

kInterpreted marker

A special cache value that means “don't try to JIT this PC again.” Crucial: the JIT must never install a real x86 entry for an interpreter-fallback PC, or you get an infinite loop of re-translation attempts.

7. NZCV Flag Emulation

ARM64 stores condition flags in NZCV (Negative, Zero, Carry, oVerflow). x86_64 stores them in RFLAGS with a different layout. Every flag-setting ARM64 op needs to leave behind something the next conditional can read in ARM's format.

For most flag-setting ops, the JIT emits the natural x86 instruction (which sets RFLAGS) and then captures the relevant bits into ARM's NZCV format using this pattern:

; after the flag-setting op (e.g. ADD, SUB, AND)
LAHF                  ; load SF, ZF, AF, PF, CF from RFLAGS into AH
SETO  AL              ; capture OF (overflow) into AL
AND   AX, <mask>      ; isolate N, Z, C, V bits
MOVW  [rbp+nzcv], AX  ; store packed NZCV into ThreadState

A subtle trap: PUSH/POP on x86_64 do not change RFLAGS, but SUB/ADD RSP, imm do. So when the JIT spills temporaries before LAHF, it has to use PUSH/POP or LEA — never SUB RSP — or the captured flags reflect the spill instead of the guest op.

8. Syscall Emulation Paths

Syscalls are always interpreter-only — they cross the kernel boundary and can have side effects the JIT can't reason about. When a guest issues SVC #0, the interpreter takes over, translates the call, runs the host syscall, and translates the result back.

futex

The guest stores its futex word at an ARM64-translated address; the host kernel reads it directly. Most cases are pass-through, but a few argument types (uaddr2, value bag) need bit-width-aware handling.

pthread_once / call_once

Naive forwarding of __cxa_guard_acquire through the proxy can deadlock when guest TLS doesn't agree with the host's view of who holds the once-flag. The kernel_api workaround short-circuits the guard for one-shot init.

mmap BSS zeroing

When an NDK 28+ APK's .so ends mid-page, the file-backed mmap leaves the page tail uninitialized. sys_mman_emulation.cc explicitly zeroes the tail so BSS appears as expected to the guest linker.

Why interpreter-only?

SVC can transfer control unpredictably (signals, exec). The JIT can't model post-syscall state safely, so the dispatcher always exits the region around a syscall.

9. Proxy Library Forwarding

If every guest API call had to be translated instruction-by-instruction down through the entire system library stack, performance would collapse. Digitalis intercepts well-known library boundaries and hands the call to the host implementation directly. Each proxy library is an ARM64 stub that marshals arguments and switches to the host x86_64 ABI.

There are 21 proxy libraries covering libc, libm, libvulkan, libEGL, libGLESv1_CM/v2/v3, libOpenSLES, libaaudio, libamidi, libandroid, libcamera2ndk, libmediandk, libbinder_ndk, libneuralnetworks, libjnigraphics, libnativewindow, and friends. The set of guest-to-proxy redirects is declared in system/etc/ld.config.arm64.txt.

10. Module Map

Where each piece of the translator lives in the AOSP source tree. All paths are under frameworks/libs/binary_translation/.

PathRole
lite_translator/arm64_to_x86_64/JIT compiler — emits x86_64 for integer, branch, load/store, system, and most SIMD ops.
interpreter/arm64/Per-instruction fallback for syscalls, complex SIMD (pairwise, widening, permute), CRC32, and scalar conversions.
decoder/include/berberis/decoder/arm64/ARM64 instruction bit-field decoding (decoder.h, semantics_player.h). Dispatch order matters — opcodes share prefixes.
runtime/arm64/Translation cache, dispatch loop, region lifecycle management.
kernel_api/Linux syscall forwarding, futex workarounds, pthread_once deadlock fixups, BSS partial-page zeroing.
guest_loader/ELF loader (TinyLoader), NativeBridge initialization, hand-off into the guest stack.
android_api/Proxy libraries — ARM64 stubs that forward to host x86_64 implementations.
prebuilt/Static configuration including ld.config.arm64.txt, which redirects guest dynamic-linker resolution onto the proxy stubs.
